# KAKEN Polaris 設計メモ（2026-09-22 議論の記録）

> 名称: **KAKEN Polaris**（ポラリス、リポジトリ名 kaken-polaris）。2026-09-23 に仮称 whet から改名。KAKEN-ATLAS（地図）に対する「北極星」＝審査基準という動かない基準点に照らして申請書を磨く、の意。

## 目的

研究者が作成した科研費申請書案（AI補助で作成したものを含む）をアップロードすると、
ブラッシュアップ用のコメントを返すサービス。
URAと研究者の面談の文字起こしを追加でアップロードすると、指摘の精度が上がる。

- 対象種目: 基盤研究(C)、基盤研究(B)、若手研究
- 基本はローカルLLMで動作（申請書は未公開研究情報のため外に出さない）
- 作成者一人の知見ではなく、多くのURAの知見を総動員して育てる

## 1. レビューエンジンの基本設計

- **審査基準に沿った構造化レビュー**を核にする。
  公開されている審査基準（学術的重要性、実現可能性、研究遂行能力、審査区分との適合）と
  様式の各欄を背骨にしたチェック観点（ルーブリック）を作り、LLMに欄ごと・観点ごとに評価させる。
- 出力はフリーな感想ではなく「該当箇所の引用、問題、改善案」の形に固定する。精度と再現性のため。
- 基盤C/B/若手は様式がほぼ共通なので、共通ルーブリック + 種目別差分の構成。
  - 若手: 着想に至った経緯、研究遂行能力の見せ方
  - 基盤B: 分担体制、予算規模の妥当性
- **面談文字起こしの活用が最も価値が高い**。
  研究者が口頭で語った本当の狙い・強みと、申請書に書けていないことのギャップを抽出する。
  「面談ではこう言っていたのに申請書に書かれていない」という指摘はURAの仕事そのもの。
  文字起こしはwhisper系でローカル処理。

## 2. 実行環境（決定事項）

- **本番: Mac Studio M5 Ultra 96GB** を各大学に用意してもらう。
  逆に、この機材をローカルで用意できる機関だけが使う、という割り切り。
- 96GBで載るモデルの目安
  - 30Bクラス密モデルの8bit、または70Bクラスの4bit（日本語長文添削の実用ライン）
  - 100B級MoE（4bitで60GB前後）も候補。生成が速い
  - 200B級以上は載らない
- 推論スタックは **MLX** を採用。OpenAI互換のローカルエンドポイントとして立て、アプリはそこを叩く。
- Apple Siliconの弱点はプロンプト処理速度。申請書（基盤Cで約2万トークン）+ 面談文字起こし（60分で約2万トークン）+ ルーブリックを一度に入れると70B級で数分かかる。
  - → **バッチ型UX**（アップロードして数分後にレポート）として設計する
  - → 欄ごとに分割して処理する
  - → 学内でのジョブキューが必要（URA数人規模なら十分）
- 同一機材・同一モデルに固定できるので、ある大学でチューニングしたルーブリックやプロンプトが他大学でも同じ挙動で再現される。これが知見共有の再現性を担保する。
- 配布は「アプライアンス」として考える
  - インストールスクリプト一式 + ハッシュで固定したモデル重み
  - 観点DBとプロンプトのリリース版（署名付きで配布、各機関がpull）
  - 機関向け要件書（機材、ネットワーク分離、管理者、申請書の保存期限と削除ポリシー）
- 学内での認証、ログの扱い、申請書データの削除規則は最初から決める。
- 開発はMacBook Air (M3, 24GB) で小さいモデル（14Bクラスまで）を使って進め、
  エンドポイント差し替えでMac Studioの本番モデルに切り替える。
  開発時にClaude APIで「お手本コメント」を作り、ローカルモデルとの差を測る使い分けも有効。

## 3. URAの知見の形式化と蓄積（肝）

### 運用フロー（案）

1. 各URAが自分の知見をmdファイルで書き出す
2. 科研費セミナー等の資料からもノウハウをmdで集める
3. 生成AIで統合し、矛盾する部分を論点として整理させる
4. オンライン会議で論点を議論し、方向を確立する
5. 会議も録音・文字起こしし、決定をノウハウに統合する

### 設計上の要点

- **申請書そのものは機関を越えて共有できない**。共有できるのは観点、チェックリスト、匿名化した指摘パターン、よくある落とし穴と改善例。
- **矛盾の大半は条件の違いであって矛盾ではない**。
  各主張に適用範囲（種目、分野・審査区分、欄、適用年度、出典、確度）を付けてから突き合わせる。
  同じ条件で逆のことを言っているものだけが真の論点として会議に残る。
- **統合結果と元資料を分ける**。
  各URAのmd、セミナー資料メモ、会議文字起こしは元資料として不変で残し、
  抽出した知見は別の層で管理。各知見には出典リンクを付ける（監査可能、様式変更時に根拠の陳腐化を判定できる）。
- **知見の単位は「カード」**。一件一ファイル、frontmatter付きmd。

```markdown
---
id: K-0042
claim: 「研究目的」冒頭で問いを一文で示し、その後に背景を置く
scope: {種目: [基盤C, 若手], 分野: 理工系, 欄: 研究目的}
status: 合意          # 提案 / 議論中 / 合意 / 却下 / 条件付き
decided: 2026-10-15
sources: [ura-A/notes.md#L12, seminar-2025-jsps.md, meeting-2026-10-15.md]
confidence: 高
---
根拠と例（before/after）をここに書く
```

  この形式なら矛盾検出を機械的にやれ、そのままレビューエンジンのルーブリックとして読み込める。
  知見の蓄積とレビュー精度向上が同じファイルで繋がる。
- **会議の文字起こしは自動でマージしない**。
  AIに「議論された論点、出た選択肢、決まったこと、理由」を決定記録の下書きとして起こさせ、
  参加者の一人が確認してからカードのstatusを更新する。
  会議前には逆に、AIに論点一覧と各主張の出典を議題メモとして作らせる。
- **フィードバックループ**を最初から組み込む。
  LLMのコメントに対するURAの採用・修正・却下の記録、可能なら採択結果を貯める。
  精度向上の元データであり、「良いコメントとは何か」の評価基準になる。
- 配布するのは「モデル」ではなく「観点DBとプロンプト」。
- セミナー資料は出典ごとに共有可否を明記する（JSPS公開資料はOK、有料セミナーや他機関内部資料は不可の可能性）。
- 合意後も却下した側の主張はstatus付きで残す（特定審査委員の好みへの過学習防止、条件付き復活の余地）。

### 道具立て

- mdカードの集合を **git で管理**。提案=ブランチ、議論=レビュー、合意=マージ。履歴と差分が自動で残る。
- URA全員にgitは現実的でないので、フォームやエディタで書いたものを裏でgitに落とす簡単なフロントを付ける。
- 矛盾検出や決定記録の下書きは、Mac Studioの同じローカルLLMで回せる。

## 4. 進め方

1. **フェーズ1**: 公開審査基準からルーブリックを作り、申請書PDFを入れると観点別コメントを返す最小版（CLIか簡易Web）。まず作成者自身の知見だけで精度を確かめる。
2. **フェーズ2**: 面談文字起こしを入れ、申請書とのギャップ抽出を追加。
3. **フェーズ3**: 観点DBを複数URAが編集できる形にし、コメントへの採否記録を貯める。

### 次の一手

- 作成者が自分の知見をmdで一つ書き出す → それをカードに分解する処理を試作する
- このディレクトリにMLXの推論環境と、ルーブリック駆動のレビュー処理の骨組みを作る

## 5. Webサービスの構成と運用（追記）

### 提供形態

- 学内ネットワーク（またはVPN）からのみ到達できるWebサービス。Mac Studio 1台にWebアプリ、ファイルDB（SQLite）、ジョブキュー、MLX推論サーバを同居させる。
- 認証: 学内SSOが使えれば理想。使えなければ学内メールアドレスでの登録確認、またはURAが発行する招待コード。
- 処理は数分かかるので「処理中」表示と完了時の学内メール通知。

### データモデル

```
研究者アカウント
└── プロジェクト（応募1件 = 種目・年度を作成時に選ぶ → 適用ルーブリックが決まる）
    ├── 面談テキスト（URAまたは研究者がアップ、複数回可。以降の全版のレビューに使う）
    ├── 版1: 申請書.docx → レポート1（AIの修正方針）
    ├── 版2: 申請書.docx → レポート2（版1の指摘の解消状況を含む）
    └── ...
```

- 入力はWord（.docx）を主とする。様式の欄見出しが固定なので欄ごとに分割して読める。図表は評価対象外と明示。
- 版を重ねると、前の版とレポートも渡して「解消された指摘・残っている指摘」を出す。版の差分表示も可能。
- URA役割: 担当プロジェクトの閲覧と面談テキストの直接添付ができる。研究者がプロジェクト作成時に担当URAを指定する。
  （初期はURAが文字起こしをメールで研究者に送り研究者がアップする運用でも可。データの持ち方を案件単位にしておけば後で切り替えられる）

### レポート（修正方針）の見せ方

- 画面上で欄ごとに「引用、指摘、改善案」を表示。
- md または Word でダウンロード可。フェーズ2で「Wordにコメントとして差し込んだファイル」を返すことを検討。
- 各指摘に「役に立った / 的外れ」ボタン → 知見DBへのフィードバック。

### 決めておくこと

- アップロードした申請書・面談テキストの保存期限（締切後の自動削除、研究者自身による削除）。
- レポートの閲覧範囲（研究者本人と担当URAまで）。

### レポートの内容方針（コピペ対策は形式ではなく内容で）

- **修正文を出さない**。レポートは「診断と方針」に限定する。
  - 指摘: 引用箇所 + 観点 + 弱さの説明
  - 問いかけ: 研究者本人しか答えられない質問（例: 失敗要因と対策は何か）
  - 構成の方針: どう直すかの方向（問いを冒頭に、面談で語った予備実験をここに、等）
- 面談テキストとのギャップ指摘は「面談で言っていたことを書け」なので本人にしか書けず、コピペの余地が自然に消える。
- 理由: 複数大学が同じモデル・同じルーブリックで動くため、修正文を出すと同じ言い回しの申請書が同じ審査区分に並ぶ。
  「本人の文章を良くする道具であって、文章を作る道具ではない」という線引きをサービスの信頼性の柱にする。
- 例文を出す場合は一文程度の「型」のみ（研究内容を含めない）。段落単位の書き換えはURAが案件ごとに明示的に有効化したときだけ。
- 形式は読みやすさで決める。画面表示が基本、印刷・保存用にPDFダウンロード。PDFによるコピー抑止は効果がないので狙わない。

## 6. 再挑戦モード: 前年度の不採択申請書 + 審査結果開示情報を起点にする（2026-09-23 追記）

### 審査結果開示情報の構造（基盤C・若手、電子申請システムの「審査結果開示」画面）

1. 種目、小区分、小委員会、研究課題名、当該年度の応募・採択件数と採択率（種目全体と小区分）
2. 不採択課題の中でのおおよその順位: A（上位20%）/ B（21〜50%）/ C（50%に至らず）
3. 評定要素 A(1)学術的重要性 / A(2)研究方法の妥当性 / A(3)遂行能力・環境 それぞれについて
   「あなたの平均点」と「当該審査区分の採択課題の平均点」（4段階）
4. 2以下を付けた審査委員がいる項目に「＊」（委員数分、最大3個）。項目は審査規程の問い（form_structure.md の「規程の問い」）と一対一
5. 評定要素B 国際性の平均点と採択課題平均（基盤A・B・Cのみ）
6. 研究経費の妥当性: 「問題がある」と評定した委員数
7. 人権保護・法令遵守: 「不十分」と指摘した委員数

→ ルーブリックの観点単位で「どこが採択ラインに届かなかったか」が数値で分かる。
   ＊が付いた項目 = 審査委員が実際に減点理由として選んだ観点なので、レビューの最優先事項になる。

### 想定する使い方

- プロジェクト作成時に「前年度不採択からの再挑戦」を選び、前年度の申請書（.docx）と開示情報を登録する。
- レビューエンジンは、通常のルーブリック評価に加えて
  - ＊付き項目に対応する観点を最優先で診断し、前年度版と今年度版の差分がその観点に効いているかを判定
  - 採択課題平均との差が大きい評定要素を「重点」として明示
  - 順位（A/B/C）から改稿の深さを助言（Bなら弱点の補強、Cなら問い・位置づけの再構成レベル）
- 面談テキストがあれば、「開示で＊が付いた観点について面談で語られた内容が申請書に反映されているか」を突合する。

### 入力方法

- 電子申請システムのPDFはフォント埋め込みの都合でテキスト抽出が文字化けする（pypdfで確認済み）。
  → 開示情報は構造が固定なので、**入力フォーム**（順位A/B/C、各評定要素の自分の平均点と採択平均、＊の付いた項目のチェック、国際性の点数、経費・人権の指摘有無）で入力してもらうのが最も確実。
  → PDFアップロードにも対応する場合は画像化してビジョンモデルまたはOCRで読む（フォーム入力の補助として）。
- 過去の開示情報は、匿名化（種目・小区分・順位・点数・＊項目のみ、課題名や本文なし）すれば機関を越えて集められる可能性がある。
  「どの観点で減点されやすいか」「採択平均はどの程度か」の統計として知見DBの材料になる。

## 7. 構造データ + 審査結果のペア収集（同意ベース）（2026-09-23 追記）

### 狙い

本文は保存せず、「申請書の構造の特徴」と「審査結果」をペアで匿名保存し、件数として蓄積する。
URAが普段入手できない「書き方と審査結果の対応」が集まる。

### 保存する項目（案）

- 構造の特徴（カテゴリ値・数値のみ、研究テーマを示す語は含めない）
  - 小項目(1)〜(6)の有無と順序、各小項目の分量（行数・文字数）、概要の行数
  - 問いが一文で明示されているか、問いの位置
  - 予備データ・予備実験の有無、年次計画の有無、研究項目の数
  - 業績の件数、国際性の記述の型（けん引 / 協同 / 独自）、図の数、分担者数、経費内訳の比率
- レビューエンジンが付けたルーブリック評価（観点ごとの水準）
- 審査結果: 種目、区分（保存時に中区分または大区分に丸める）、年度（幅で持つ）、順位A/B/C、評定要素ごとの点数と採択平均、＊項目、採否

### 得られるもの

1. LLMのルーブリック採点と審査委員の実採点の突合 → 水準記述のずれの検出（レビュー精度の正解データ）
2. 知見カードの裏付け（「問いを冒頭に」と学術的重要性の点数の関係など）→ カードの重み付けの根拠
3. 区分ごとの相場（採択平均、＊が付きやすい観点）

### 同意と匿名化

- 保存するJSONそのものを画面に表示し、項目ごとに外せる形で同意を取る。後から取り下げ可能。
- 作業用データ（申請書本文・面談テキスト）とは物理的に分離して保存。
- 小区分 × 年度 × 採否の組み合わせで再識別され得るため、区分の丸め、年度の幅、件数閾値未満の組み合わせは非表示、を保存・集計の両方で行う。
- 機関を越えて持ち寄る場合は参加機関間の合意文書とスキーマの固定が前提。学内の個人情報の扱いも事前に確認。

### 使い方の線引き

- 相関であって因果ではない（利用者の偏り、相対評価）。カードの重み付けの根拠に使い、「この構造なら通る」という自動ルールにはしない（画一化防止、第5節のレポート内容方針と同根）。

### 実装上の位置づけ

- 構造抽出はレビュー処理の副産物として毎回出せる（欄ごとに読んだ時点で特徴は手元にある）。
- 採否は翌年に判明するため、プロジェクトに「後から審査結果を登録する」導線を作り、同意済み構造データに後追いで紐づける。

### 擬似審査（評点の付与）の扱い（2026-09-23 追記）

- **総合評点と採否は予測しない。** 総合評点は小区分内の相対評価で分布が強制される（審査の手引）。一件の調書からは原理的に出せない。
- **評定要素の点数（絶対評価）も、研究者向けの既定表示では数値を出さない。** LLMの採点と審査委員の採点の対応（較正）が取れるまでは、数値は根拠のない安心や不安を生む。数値は引用されやすく、機関内で独り歩きする。
- 代わりに出すもの:
  - 観点ごとの水準を「観察された状態」の言葉で示す（例: 問いが目的文の形になっている）。水準の数字は状態のラベルであり予測ではない。
  - 「審査委員が2以下を付ける可能性がある項目」のフラグ一覧。開示情報の＊項目と同じ形式なので、研究者が実際に受け取る審査の像に対応する。
  - 200字程度の模擬審査意見（長所・短所）。「視点の例」と明記。
- 数値は内部に保持する（URA表示モードで閲覧可、第7節の較正データとして蓄積）。開示情報との突合で相関が確認できた観点から、信頼区間付きで表示を解禁する。
- 免責の定型文をレポートに常時付ける（審査は相対評価で審査委員3名の見識に依存する、本レポートは記述の弱点を示すもので採否を予測しない）。

## 8. KAKEN-ATLAS の埋め込みとの連携（2026-09-23 追記、検討中）

- kaken-atlas は採択課題 206,078 件の研究概要を Ruri v3（cl-nagoya/ruri-v3-310m、768次元）で埋め込み済み（Hugging Face rma-lab/kaken-atlas-embeddings、CC BY 4.0）。
- 申請書の「概要」（10行）と学術的「問い」を同じモデルでローカルに埋め込み、コサイン類似で近傍 k 件（k=50 程度）を引く。
  - 近傍の小区分分布 → 選んだ小区分の妥当性の目安（R19 の材料）。上位3区分の割合と近傍課題名3件を示す
  - 近傍の採択課題 → 位置づけ（R06）・独自性（R04）を書く際の「隣にある既採択研究」の提示
- 方針: **まず kNN（学習不要）**。分布と近傍の実例で根拠を示せる、審査区分表の改正に追従しやすい、複数所属の小区分や応募者の区分選択の揺れ（ラベルのノイズ）に強い。
  ファインチューニングした分類器（過去に実施）は top-1 精度では勝る可能性があるが、306クラスの不均衡、再学習の手間、根拠の説明のしにくさがあり、KAKEN Polaris の用途（単一ラベルではなく「妥当か、他の候補は何か」）には kNN の方が合う。必要なら kNN の投票を分類器として較正するか、両者を併記する
- 注意: 埋め込み対象は採択時の研究概要（短文）なので、申請書側も概要相当の短文を埋め込む（長文全体ではなく）。審査の手引どおり区分選択だけでは減点されないので「参考情報」と明示する。近傍課題は「参考」であり文章を寄せる方向には使わない（画一化防止）
- 実装: Ruri v3 310m は Mac 上で軽く動く。申請書は学外に出ない。埋め込みデータは公開物なので各機関のアプライアンスに同梱できる

### KAKEN データのその他の利用価値（2026-09-23 追記）

ルーブリックの観点に対応させて整理。
- R04/R06 位置づけ・独自性: 近傍の採択課題を「既に助成されている隣接研究」として提示
- R05 今取り組む理由: 近傍領域の年度別採択件数の推移（kaken-atlas の成長性指標）
- R07/R10 到達目標・波及効果: 研究成果報告書「研究成果の概要」＝同種課題が3〜5年で実際に到達した記録
- R13 経費の相場: 小区分×種目ごとの配分額分布
- R15 研究遂行能力: 応募者本人の過去の採択課題・成果報告（公開情報）と、準備状況・経緯・前年度応募欄の記述との突合
- ルーブリックの較正: 小区分ごとの採択課題の概要の相場（長さ、問いの形、用語密度、構成の型）。第7節の構造データが貯まるまでの代替
- 運用: 小区分ごとの採択件数・種目構成（競争の激しさ、若手→基盤Cの移行）、基盤Bの分担者候補探し（kaken-atlas 既存機能）

限界: 採択課題のみ（不採択との対比不可、生存者バイアス）。概要は採択後に書かれた「研究開始時の概要」で申請書そのものではない。採択概要に文章を寄せる使い方は画一化を招くので、分析と提示にとどめ型として真似させない。
最初に効くのは位置づけの提示と「今」の根拠。kaken-atlas の既存資産だけで動く。

### 申請書を kaken-atlas の地図上にプロットする（2026-09-23 追記）

- kaken-atlas は UMAP の座標のみ保存（reducer 未保存）。新規点の transform は現状不可。
- 方針: 近傍配置。概要の埋め込み → 768次元でコサイン近傍 k 件（15〜50） → 近傍課題の地図座標を類似度で重み付き平均。2D/3D/球面のいずれにも同手順で置ける。区分判定と同じ近傍計算の副産物。
- 表示: 地図に申請書の点を一つ打ち、近傍課題を強調。「近傍からの推定で正確な座標ではない」と明示。近傍が散らばる場合は「複数領域にまたがる提案」として見せる（区分選択でも迷う提案）。
- 秘匿: 埋め込み計算は学内Mac。地図は学内に複製して点を重ねる。公開サイトには何も送らない。kaken-atlas 側に「ローカルJSONから外部点を重ねる」機能（ネットワーク送信なし）を足せば足りる。
- 将来: kaken-atlas が reducer を保存すれば UMAP transform に置き換え可。
