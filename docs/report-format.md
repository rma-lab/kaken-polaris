# 修正方針レポートの一例（2026-09-23、作成者の実例5件から抽出。参考資料）

作成者（荻）が令和9年度公募向けに Claude を併用して作成した修正方針レポート5件（基盤B 1件、基盤C 3件、若手 1件。4〜9頁、6千〜1.1万字）から、共通する構造と技法を抜き出したもの。研究者名・研究内容は含めない。

**位置づけ**: これは作成者がこれまで試行してきたやり方の記録であり、正解や到達目標ではない。砂時計モデル等の技法は作成者個人の主観に基づく作業仮説で、効果は検証されていない。Polaris のレポート形式を設計するときの参考の一つとして扱い、他のURAの流儀や資料分析の結果と並べて相対化すること。

## 1. 共通する構造

| 部 | 内容 | 5件中 |
|---|---|---|
| ヘッダー | 課題名、種目、小区分、研究期間、対象版（受領日・版番号）、作成者、作成日、**生成AI関与の明示** | 5 |
| 凡例 | 【荻】URAの判断／【AI】AIの分析をURAが採用／【荻・AI】両者の照合／【要確認】研究者に事実確認／◆ 修正提案（採否は研究者の判断）／優先度 A 採否に直結・B 評点に影響・C 表記 | 4 |
| 0. 総括 | 「まず直すべき3点」。表形式（優先／問題／要点／参照節）。冒頭に調書の強みを一段落 | 5 |
| 1. 審査員はこの調書をどう読むか | 専門外の審査委員が本文だけから理解する筋書きを再構成した要約。意図とのズレを検出する | 3 |
| 2. 構造診断（砂時計モデル） | 背景（広）→問い（狭）→目的（最も狭）→独自性・波及・国際性（再び広）の各層について「現在の記述／診断」の表 | 4 |
| 3〜5. 欄ごとの診断 | 様式の欄・小項目ごとに、優先度付きの指摘 → ◆修正の方向（案が複数あるときは 案(a)/(b) と利点・留意点の表） | 5 |
| 6. 修正作業の順序 | 時間が限られる場合の優先順 | 4 |
| 7. 【要確認】一覧 | 研究者にしか答えられない事実確認をまとめて列挙 | 4 |
| 8. 位置づけと注意事項 | AI関与に関する4点（後述） | 4 |

並べ方は2通りあった。**優先度順**（総括→構造→内容→表記）と**様式順**（欄1(1)から経費まで）。前者は初版・大改稿向き、後者は骨格が固まった版の点検向き。第2版は「前版からの追加」「確認事項への回答の反映」を冒頭に書く。

## 2. 繰り返し使われている技法（作成者個人の作業仮説。検証されていない）

| 技法 | 内容 | 対応するルーブリック観点 |
|---|---|---|
| **砂時計モデル** | 背景→問い→目的で絞り、独自性・波及・国際性で広げる。層ごとに「同じ高さにある」「逆転している」を診断する | R01〜R07 の横断 |
| **目的の3テスト** | ①達成判定（終了時に Yes/No で判定できるか）②成果報告（成果報告書に書ける形か）③主語（主語が申請者の行為になっているか） | R10（到達目標）、R02 |
| **差し替えテスト** | その文をライバル研究者が書いても同じ文になるなら、申請者固有の記述ではない。問い・経緯・独自性に適用 | R02, R03, R04 |
| **先取り問題** | 背景・経緯の段階で解決策を先取りして書いていないか。仮説の提示で止めるべき箇所を判定 | R03（新規の減点側） |
| **同文の繰り返し** | 同じ仮説文が問い・独自性・経緯で3回出る等。役割ごとに書き分け、読み疲れを防ぐ | R20（分量）、R19 |
| **研究の残余** | 準備状況と業績が踏み込みすぎると「残っているのは刊行だけ」と読まれる。既知／未知の線引きを明示する | R12（上限）、R10 |
| **専門外の読者再構成** | 本文だけから専門外向けの要約を書き、審査委員が持つ疑問を2〜3個挙げる | R19 |
| **競合の名指し** | 研究動向で主要グループを落としていないか。「限られている」という主張の裏取り | R06 |
| **目的と研究項目の対応表** | 目的①②③に対応する研究項目があるか、準備状況に「実施済み」として逃げていないか | R08 |
| **数を問う** | 被験者数・型の数・判定基準・対象数・回数。「n はいくつ」を審査委員は必ず問う | R09 |
| **事実誤りの優先扱い** | 機関名・事業名・書誌の誤りは調書全体の信頼を損なうので A に準じる | R16, R18（減点側） |
| **分担者の役割の接続** | 分担者の強みがどの研究項目に効くかを明示する | R14 |
| **白黒化の判読** | カラーマップは白黒で判読できるか、線種・マーカーで区別、キャプションで「何が見えれば主張が成り立つか」 | R20 |
| **既存コメントとの照合** | 学内レビュアーのPDFコメントと照合し「同旨」を明記。指摘の重複を避ける | 入力データ |
| **ウェブ調査** | researchmap・KAKEN で過去課題・業績を確認し、調書内の記述と突合（前課題との重複、残余問題） | R15、KAKEN連携 |
| **減点材料の視点** | 「採択率3割の審査で、不採択理由として書きやすい箇所」を優先度Aにする | 横断 |

## 3. 文案の扱い（設計メモ第5節との関係）

実例には「問いの案（2案）」「目的の案」「研究項目の文案」が含まれる。ただし次の条件付き。

- ◆印は「素材であり、最終的な文言は先生方のもの」と明記
- 文案中の【 】は研究者が確認・記入する箇所（数値、固有名、判断）で、AIが埋めない
- 案は複数提示し、利点と留意点を並べて選ばせる
- 文案はURAが検証したうえで出している（【荻・AI】）

→ 実例ではこの条件で文案を出していた。設計メモ第5節（2026-09-23 改訂）では、研究者向けにも「方向 → 書くべき要素の箇条書き → 【 】穴埋めの型」の三段階で修正案を出し、コピペできる完成文は出さない、と整理した。要素の箇条書きは一般論ではなく、その課題に特有の語（対象・手法・先行研究のグループ・予備データ・面談で語られた事実）で具体的に書く。実例の「問いの案」「目的の案」は、型と【 】の形に寄せれば研究者向けにも使える。

## 4. AI関与の注意書き（実例の定型）

1. 生成AIは断定調で出力する傾向があり、断定的に見える箇所ほど根拠の確認を
2. AIは研究コミュニティでの合意形成・受容状況（審査委員がその分野で何を常識と見なすか）までは評価できない
3. 提案は申請者自身の専門的判断による取捨選択（二段階検証）を前提とする
4. 引用文献は、書誌の実在確認と内容の正しさの検証を別物として扱う

→ Polaris のレポート末尾の注意書きを考えるときの参考。

## 5. Polaris の設計で検討したい点（実例からの示唆。決定ではない）

- 実例では URA が AI の分析を照合・採用・棄却して【荻】【AI】【荻・AI】を付けていた。Polaris の出力を「URAが手を入れる前の層」と見なす設計は一案
- 観点21個を並べるより、採否に直結するものを少数に絞って先に出す方が読まれやすい可能性がある
- 専門外の読者による要約の再構成は、R19 の判定の補助になり得る
- 【要確認】の一覧化は、ルーブリックの questions の集約に近い
- 技法の多くは観点をまたぐ（差し替え、3テスト、残余、先取り）。カード化するなら、観点ではなく複数観点にかかる「テスト」として、作成者個人の仮説であることを明記して持つ
- 学内レビュアーのコメントや researchmap・KAKEN の照会結果を入力に含めるかは検討事項
